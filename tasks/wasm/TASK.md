## Goal

Implement a MoonBit **WebAssembly 3.0 binary decoder, module validator
and text-format printer** that is compatible with this repository's test
suite. The authoritative references are vendored in:

- `specs/WebAssembly-3.0.pdf` — the WebAssembly Core Specification,
  Release 3.0 (2026-07-10), the standard this task follows
  (`specs/WebAssembly-3.0.txt` is a plain-text rendering of it for
  grepping; `specs/w3.txt` records the provenance of both)
- `specs/wasm.md` — this repo's implementation-oriented summary, with
  section references into the release, and the printing conventions the
  snapshots pin

## What This Task Is Really About

This is an exercise in implementing a **real binary format** end to end:

- A **decoder** that accepts exactly the byte strings the binary grammar
  generates — LEB128 with the spec's length and unused-bit rules, strict
  UTF-8 names, section order and size accounting, every type and
  section form of Release 3.0 (recursive groups and sub types,
  struct/array types, 64-bit address types, tags, all element/data
  segment encodings), and every instruction of the 3.0 instruction set
  with its immediates — and raises on anything *malformed*
- A **validator** for the module-level rules of the Validation chapter:
  well-formed type definitions and subtyping (iso-recursive type
  equivalence), limits, constant expressions type-checked under the
  subtyping relation, segment/table/memory consistency, start and
  export rules — raising on *invalid* modules. Type-checking the
  instruction sequences inside function bodies is out of scope (see
  *Scope*).
- A **printer** producing the text format in one fixed flat layout
  (`specs/wasm.md` § Printing): index comments, the abbreviations for
  reference types and sub types, hexadecimal float constants with a
  decimal comment, escaped names and data strings, and function bodies
  with two-space nesting.

**Important mindset**: the corpus was generated by a fuzzer and covers
the type system broadly, but if it were regenerated with different
modules your implementation should still pass. If it wouldn't, you
haven't built a decoder — you've built a lookup table.

## Approach

Build incrementally:

1. **Reader**: bounded byte reader, strict LEB128 (`u32`, `u64`, `s32`,
   `s33`, `s64`), little-endian floats, UTF-8 names.
2. **Sections**: preamble, section order/size accounting, custom
   sections; types (rec groups, sub types, composite types, reference
   and packed types), imports, functions, tables, memories, tags,
   globals, exports, start, element segments (all eight forms), data
   count, code (locals + body), data.
3. **Instructions**: the full opcode table including the `0xFB`, `0xFC`
   and `0xFD` prefixes, block structure (`block`/`loop`/`if`/`else`/
   `try_table`/`end`), memargs, lane immediates.
4. **Printing**: definitions in canonical order with `(;N;)` index
   comments, then bodies; get floats and string escapes exactly right.
5. **Validation**: type well-formedness and subtyping with canonical
   (iso-recursive) type equivalence, limits, constant expressions,
   segments, start, exports.

Run tests frequently while adding features.

Important: The core logic must be implemented in MoonBit.

## Scope

In scope (WebAssembly 3.0, exactly):

- Decoding: the complete binary format of Release 3.0 — all sections
  and every instruction — with every malformedness condition of the
  grammar (bad preamble, unknown/duplicated/misordered sections, size
  mismatches, over-long or over-wide LEB128, invalid UTF-8, unknown type
  codes and opcodes, missing `end`, function/code and data-count
  mismatches, a data index without a data count section).
- Validation (module level): type definitions and subtyping, limits,
  function/tag types, valid value types, constant expressions, table
  initializers, data and element segments, start, exports.
- Printing: the flat text format described in `specs/wasm.md`,
  including function bodies (every instruction of the 3.0 set).

Out of scope:

- Type-checking instruction sequences inside function bodies (§3.4.12
  of the release): `validate_module` must not reject a module on account
  of its function bodies. A solver that does type-check bodies is not
  penalised — every module the suite calls valid has well-typed bodies.
- Executing WebAssembly; parsing the text format.
- Proposals that are not part of Release 3.0 (threads/shared memories,
  stack switching, custom page sizes, wide arithmetic, legacy exception
  handling): their encodings are **malformed**.
- Interpreting the `name` custom section: all indices print numerically.

## Required API

Complete the declarations in `wasm_spec.mbt`.

Implementation notes:

- You can **freely decide** the project structure (modules/files), the
  decoding/validation strategy, and any internal data structures.
- Do **not** modify the following files:
  - `wasm_spec.mbt` - API specification (`Module`, `decode_module`,
    `Module::print`, `validate_module`)
  - `specs/` folder - Reference documents
  - `*_pub_test.mbt` - Public test file (`wasm_pub_test.mbt`)
  - `*_priv_test.mbt` - Private test file (`wasm_priv_test.mbt`)
  - `wasm_qc_test.mbt` - Property-test generators and tests
- Implement the required declarations by adding new `.mbt` files as needed.
- **You may add additional test files** (e.g., `xxx_test.mbt`) if needed
  for testing and maintenance purposes:
  - Create test files to validate edge cases
  - Derive test scenarios from the specification
  - All added tests must remain faithful to WebAssembly 3.0

Required entry points:

- `@wasm.decode_module(data : Bytes) -> Module raise`
- `@wasm.validate_module(mod_ : Module) -> Unit raise`
- `@wasm.Module::print(self : Module) -> String`

`Module` is declared abstract in `wasm_spec.mbt`: define it however you
like. Tests only construct byte strings, decode them, print the result
and validate it.

## Behavioral rules

- Follow WebAssembly 3.0 exactly; encodings from other proposals must be
  rejected as malformed.
- Keep the two failure categories apart: `decode_module` raises for
  every malformed input and only for malformed input; `validate_module`
  raises for every invalid module and only for invalid modules. A
  well-formed but invalid module must decode and print.
- `print` never raises and is deterministic; its exact layout is fixed
  by `specs/wasm.md` § Printing and by the snapshots (custom sections
  are not printed; the `name` section is not interpreted).
- Floats print in hexadecimal significand form with a `(;=decimal;)`
  comment holding the shortest round-tripping decimal in positional
  notation; names use `\u{hex}` escapes and data strings `\hh` escapes.
- Validation covers the module-level rules listed in `wasm_spec.mbt`
  (types, limits, constant expressions, segments, start, exports).
  Body typing is out of scope: `validate_module` must not reject a
  module on account of its function bodies; type-checking them anyway is
  allowed and not penalised, because every module the suite calls valid
  has well-typed bodies.
- The decoder must never panic, whatever the input; the property test
  `quickcheck: decoding arbitrary bytes never panics` feeds it random
  section-shaped garbage.

## Constraints

### 1. Test Requirements

**All tests must pass for task completion**:

The model should keep running until all tests pass.

- **Public tests** (`*_pub_test.mbt`, `wasm_qc_test.mbt`): 119 cases in
  `wasm_pub_test.mbt` plus two property-based tests in
  `wasm_qc_test.mbt`, visible in this repository for development and
  debugging
- **Private tests** (`*_priv_test.mbt`): 863 additional cases
  that decide the score. They are **withheld while you work** — expect
  them to be absent from this directory, and do not go looking for
  them. Your `moon test` therefore exercises the public tests only;
  the private suite is run against your implementation afterwards.

**CRITICAL - Full Suite Evaluation**:

Passing only the public tests is **INSUFFICIENT**. A green `moon test`
is necessary but not sufficient: it covers roughly 12% of the cases that
decide the outcome. The task is complete only when the private suite
passes too — and you cannot run it yourself.

**Why Private Tests Matter**:
- **Coverage**: Private tests represent ~88% of the total evaluation -
  they are the primary measure of success
- **Comprehensiveness**: Validate the full binary format and the
  module-level validation rules, including edge cases, corner cases, and
  subtle rules not exposed in public tests
- **Real-world scenarios**: Test combinations and patterns that occur in
  fuzzer-generated and hand-written modules but may not be obvious from
  the spec
- **Implementation integrity**: you cannot see these cases, so the only
  way to pass them is a genuine implementation rather than a lookup table
  for the fixtures you can see

**Evaluation Process**:

Make the public tests pass by running `moon test` in this directory, and
iterate until they do, then `finish`.

There is **no submission step and no evaluation server** in this
environment: `moon test` is the command you run, and the withheld private
tests are run against your implementation afterwards.

Because the withheld tests (~88% of the suite) decide success, a genuine,
general implementation is essential: do **not** hardcode or memorize
responses to the fixtures you can see — build a real decoder, validator
and printer that work for arbitrary WebAssembly 3.0 modules.

### 2. Code Quality Requirements

**Correctness**:
- Zero compiler errors, warnings, or diagnostics
- No runtime panics or unhandled edge cases
- Proper error handling with meaningful error messages

**Formatting**:
- Run `moon fmt` to format all code
- Run `moon info` to generate interface files (`.mbti`)
- Follow MoonBit style conventions consistently

**Implementation Integrity**:
- Solutions must be real decoders/validators/printers, not
  test-specific lookup tables
- No hardcoded mappings derived from test fixtures
- Implementation should work for arbitrary WebAssembly 3.0 modules

### 3. Software Engineering Standards

**Modularity and Organization**:
- The required declarations in `wasm_spec.mbt` belong to the root `wasm`
  package. Tests call the root-package API `@wasm.decode_module`, so
  those declarations must be implemented in (or forwarded to) the root
  package.
- You may organize implementation across root-level files by functional
  area (for example, reader, decoding, instructions, validation,
  printing).
- If you create subdirectories as separate MoonBit packages, wire them
  through package configuration and keep root-package implementations,
  `pub using` re-exports, or forwarding functions so the required root
  `wasm` API remains available.
- Group related functionality together
- Avoid dumping all code in the root directory

**File Size Limits**:
- Please try to keep each file to at most **1000 lines of core code**
  (excluding blank lines and comments)
- Split large modules into focused, single-responsibility files
- Use meaningful file names that reflect their purpose

**Readability**:
- Clear, descriptive function and variable names
- Add comments for complex algorithms or non-obvious logic
- Document public APIs and key data structures
- Keep functions focused (prefer multiple small functions over large
  monolithic ones)

**Code Structure**:
- Logical separation of concerns (reading → decoding → validation →
  printing)
- Minimize coupling between modules
- Use appropriate abstractions (types, enums, structs)
- Avoid global mutable state

**Example directory structure**:
```
wasm/
├── moon.mod
├── moon.pkg
├── wasm_spec.mbt          # API specification (do not modify)
├── wasm.mbt               # Main entry point
├── reader.mbt             # Bounded reader, LEB128, UTF-8
├── types.mbt              # Abstract syntax of a module
├── decode.mbt             # Sections
├── instructions.mbt       # Opcode table and immediates
├── validate.mbt           # Module-level validation and subtyping
└── print.mbt              # Text-format printing (floats, escapes)
```

These standards ensure your code is maintainable, understandable, and
follows professional software engineering practices.
