# WebAssembly 3.0 binary decoding, validation and printing — specification for this repo

This document is a **practical, test-oriented spec** for the `wasm`
package. It summarizes the behavior required of the three entry points
declared in `wasm_spec.mbt` and pins every formatting convention the
test snapshots rely on.

It is **not** a copy of the WebAssembly specification; the authoritative
text is the *WebAssembly Core Specification, Release 3.0 (2026-07-10)*,
vendored next to this file as `WebAssembly-3.0.pdf` (the release
artifact) with a mechanical plain-text rendering `WebAssembly-3.0.txt`
for grepping (`w3.txt` records the provenance). Section numbers (§) below
refer to that release.

## Objectives (what the implementation must do)

1. `decode_module(data : Bytes) -> Module raise` — decode a binary
   module exactly as the *Binary Format* chapter's grammar (§5) generates
   it — "a byte sequence is a well-formed encoding of a module if and
   only if it is generated by the grammar" (§5.1) — and raise on every
   *malformed* input.
2. `validate_module(mod_ : Module) -> Unit raise` — check the
   module-level rules of the *Validation* chapter (§3; validity is defined
   in §3.1) and raise on every *invalid* module. Type-checking the
   instruction sequences inside function bodies (§3.4.12) is out of
   scope: `validate_module` must not reject a module on account of its
   function bodies, and a solver that does type-check bodies is not
   penalised, because every module the suite calls valid has well-typed
   bodies.
3. `Module::print(self) -> String` — render the module in the *Text
   Format* (§6) in the fixed flat layout described under *Printing*.

The tests exercise all three: valid modules are decoded, printed
(compared byte-for-byte) and validated; malformed inputs must make
`decode_module` raise; invalid modules must decode, print, and make
`validate_module` raise. Two property-based tests (generators in
`wasm_qc_test.mbt`) decode, print and validate generated modules and
feed arbitrary bytes to the decoder (which must never panic).

## Dialect

The dialect is **WebAssembly 3.0 exactly**: the MVP plus every proposal
integrated in Release 3.0 as listed in its change history (§7.8.2:
extended constant expressions, tail calls, exception handling with
`try_table`, multiple memories, 64-bit address types, typed function
references, garbage collection, relaxed SIMD, custom annotations, on top
of the 2.0 features of §7.8.1). Proposals that are **not** part of
Release 3.0 are outside the dialect and their encodings are *malformed*:

- the threads proposal's `shared` limits flags (`0x02`, `0x03`, and the
  64-bit `0x06`, `0x07`) — the release's limits grammar (§5.3.9) has
  exactly `0x00`, `0x01`, `0x04`, `0x05` — and shared globals
  (mutability byte `0x02`),
- the stack-switching heap types `cont`/`nocont` (`0x68`, `0x75`),
- the legacy exception-handling opcodes (`try`, `catch`, `rethrow`,
  `delegate`, `catch_all`: `0x06`, `0x07`, `0x09`, `0x18`, `0x19`),
- anything else not in the Release 3.0 grammar.

Custom sections are skipped by the decoder (name validity is still
checked) and never printed — the `(@custom …)` annotations of §7.7 are
optional in the text format and are not emitted; the `name` custom
section is *not* interpreted, so every index prints numerically.

## Binary format (decoding)

The input is well-formed iff the binary grammar generates it. The
decoder has to enforce the grammar; the list below names the checks the
tests lean on.

### Preamble and sections (§5.5.2, §5.5.3, §5.5.17)

- Magic `00 61 73 6D`, version `01 00 00 00`. Anything shorter, a
  different magic or a different version is malformed.
- Section ids: 0 custom, 1 type, 2 import, 3 function, 4 table, 5
  memory, 6 global, 7 export, 8 start, 9 element, 10 code, 11 data, 12
  data count, 13 tag. Any other id is malformed.
- Non-custom sections occur at most once and in this order: type,
  import, function, table, memory, **tag**, global, export, start,
  element, data count, code, data (§5.5.17). Custom sections may appear
  anywhere.
- A section's size is a `u32`; the contents must consume exactly that
  many bytes (no trailing bytes, no reading past the size) and the size
  must not exceed the remaining input (§5.5.2: "the module is malformed
  if the size does not match the length of the binary contents").
- The function and code sections must have the same number of entries.
  The data count section, when present, must equal the number of data
  segments; it must be present when `memory.init`, `data.drop`,
  `array.new_data` or `array.init_data` occurs in any function body
  (§5.5.15, §5.5.17).

### Values (§5.2)

- `uN`: unsigned LEB128, at most ceil(N/7) bytes, bits above N in the
  last byte zero. `sN`: signed LEB128, same length bound, the unused
  bits of the last byte equal to the sign bit (§5.2.2). Trailing zero
  bytes within the bound (`0x83 0x00`) are well-formed; `0x83 0x10` as a
  `u8` is not. Heap type indices and block type indices are `s33`;
  `i32.const` / `i64.const` take `s32` / `s64`; `u64` is used for limits
  and memarg offsets.
- Floats are 4/8 little-endian bytes (§5.2.3); `v128.const` and
  `i8x16.shuffle` take 16 raw bytes.
- Names are `u32`-prefixed byte strings that must be valid UTF-8 (no
  overlong encodings, no surrogates, nothing above U+10FFFF, no
  truncated sequences) (§5.2.4).
- A list length that exceeds the remaining input is truncated input.

### Types (§5.3)

- Value types: `0x7F` i32, `0x7E` i64, `0x7D` f32, `0x7C` f64, `0x7B`
  v128, reference types.
- Heap types: abstract `0x73` nofunc, `0x72` noextern, `0x74` noexn,
  `0x71` none, `0x70` func, `0x6F` extern, `0x6E` any, `0x6D` eq, `0x6C`
  i31, `0x6B` struct, `0x6A` array, `0x69` exn; concrete: a
  non-negative `s33` type index.
- Reference types: `0x63 ht` (nullable), `0x64 ht` (non-null), or a bare
  abstract heap type byte (nullable shorthand).
- Composite types: `0x60` func (params, results), `0x5F` struct (field
  list), `0x5E` array (field). Field: storage type (`0x78` i8, `0x77`
  i16, or a value type) then mutability `0x00`/`0x01`.
- Sub types: `0x50 supers* comptype` (non-final), `0x4F supers*
  comptype` (final), or a bare composite type (final, no supertypes).
  Recursive groups: `0x4E vec(subtype)`; a bare sub type is a singleton
  group. The decoder must remember whether `0x4E` was written — the
  printer shows it.
- Limits: `0x00 min` (i32), `0x01 min max` (i32), `0x04 min` (i64),
  `0x05 min max` (i64); bounds are `u64`. Table type: reference type
  then limits. Memory type: limits. Global type: value type then
  mutability. Tag type: `0x00` then a type index.

### Module fields (§5.5.4–§5.5.16)

- Import descriptors: `0x00 typeidx`, `0x01 tabletype`, `0x02 memtype`,
  `0x03 globaltype`, `0x04 0x00 typeidx` (tag). Export descriptors:
  `0x00`..`0x04` (func, table, memory, global, tag) then an index.
- Table entries: a table type, or `0x40 0x00 tabletype expr` for a table
  with an initializer.
- Global: global type then a constant expression (instructions up to
  `end`).
- Element segments, flags `0`..`7` exactly as in the spec's element
  section grammar: bit 0 passive/declarative, bit 1 explicit table
  index (active) or declarative (non-active), bit 2 expression items
  with a reference type (otherwise an element kind byte that must be
  `0x00` and function indices). Data segments: `0` active memory 0, `1`
  passive, `2` active with explicit memory index.
- Code entries: a `u32` size, local declarations as `(count, valtype)`
  pairs whose total count must fit in a `u32`, then the body. The body is
  an expression terminated by `end`, and the `end` must land exactly at
  the declared size.

### Instructions (§5.4)

Every opcode of Release 3.0 must be recognized together with its
immediates, so that bodies can be checked for well-formedness and
printed. §7.10 "Index of Instructions" is the complete list; the shapes
of immediates are:

- block types: `0x40`, a value type, or a non-negative `s33` type index;
- `br`, `br_if`, `call`, `return_call`, `call_ref`, `return_call_ref`,
  `local.*`, `global.*`, `table.get/set`, `ref.func`, `throw`,
  `br_on_null`, `br_on_non_null`: one `u32`; `br_table`: a `u32` list
  then a `u32`; `call_indirect` / `return_call_indirect`: type index
  then table index; `select t*`: a value type list; `try_table`: block
  type, then catch clauses `0x00 tag label`, `0x01 tag label`, `0x02
  label`, `0x03 label`;
- memarg: `u32` flags then `u64` offset; flags below `0x40` are the
  alignment exponent, `0x40`..`0x7F` additionally introduce a `u32`
  memory index after the flags, `0x80` and above are malformed;
- `memory.size`/`memory.grow`/`memory.fill`: a memory index;
  `memory.copy`: destination then source; `memory.init`: data index then
  memory index; `table.init`: element index then table index;
  `table.copy`: destination then source;
- `ref.null ht`; `ref.test`/`ref.cast` (`0xFB 20..23`): a heap type;
  `br_on_cast`/`br_on_cast_fail` (`0xFB 24`, `25`): a flags byte (bit 0
  first type nullable, bit 1 second type nullable, other bits malformed),
  a label, two heap types; `struct.*`/`array.*`: type index and, where
  applicable, field/data/element index or size;
- vector instructions `0xFD n` (`n` a `u32`): loads/stores take a
  memarg, `v128.const` 16 bytes, `i8x16.shuffle` 16 lane bytes,
  extract/replace lane one lane byte, `*_lane` loads/stores a memarg then
  a lane byte.

The instruction stream of an `if` may contain one `else` (`0x05`); an
`else` anywhere else is malformed.

## Validation (module level, §3)

`validate_module` checks the rules of the *Validation* chapter for
types (§3.5.1), imports (§3.5.11), tags (§3.5.2), globals (§3.5.3),
memories (§3.5.4), tables (§3.5.5), function declarations (type and
locals, §3.5.6–§3.5.7), data and element segments (§3.5.8–§3.5.9), the
start function (§3.5.10), exports (§3.5.12) and the module as a whole
(§3.5.13). **Type-checking the instruction sequences of function bodies
(§3.4.12) is out of scope**: `validate_module` must not reject a module
on account of its function bodies. A solver that does type-check bodies
is not penalised — every module the suite calls valid has well-typed
bodies (they were checked with a full validator).

### Types and matching (§3.2.11, §3.3)

- Every type index occurring in a composite type must be smaller than
  the number of types defined up to and including the enclosing
  recursive group (forward references within a group are fine).
- A sub type has at most one supertype; the supertype's index is smaller
  than the sub type's own index; the supertype is not final; and the sub
  type's composite type matches the supertype's:
  - function types: same arity, each parameter of the supertype matches
    the corresponding parameter of the subtype (contravariance), each
    result of the subtype matches the supertype's (covariance);
  - struct types: the subtype has at least as many fields and each
    common field matches;
  - array types: the fields match;
  - fields: equal mutability; immutable fields covariant in their storage
    type, mutable fields invariant (both directions); packed types only
    match themselves.
- Heap type matching (section *Matching*): `none` ≤ every abstract or
  concrete type under `any`; `nofunc` ≤ `func` and every function type;
  `noextern` ≤ `extern`; `noexn` ≤ `exn`; `i31`, `struct`, `array` ≤
  `eq` ≤ `any`; a concrete struct/array/func type ≤ `struct`/`array`/
  `func`; a concrete type ≤ another concrete type when they are
  equivalent or related through declared supertypes.
- Type equivalence is **iso-recursive**: two recursive groups that are
  syntactically equal after replacing intra-group indices by their
  position (and other indices by the canonical identity of the type they
  name) define pairwise equal types, wherever they appear in the module.
- A reference type `(ref null? ht1)` matches `(ref null? ht2)` iff it is
  not nullable or the target is, and `ht1` matches `ht2`. Number and
  vector types match only themselves.

### Limits and external types (§3.2.12–§3.2.17)

- Memory limits are valid within 2^16 pages for the i32 address type and
  2^48 for i64; table limits within 2^32−1 and 2^64−1. A minimum must
  not exceed the maximum.
- Functions (imported and defined) and tags must refer to function types;
  a tag's function type has no results.
- Global, local, table element and element segment types must be valid
  (type indices in range).

### Constant expressions (§3.4.13)

Global initializers, table initializers, element/data offsets and
element items are constant expressions: only `t.const`, `v128.const`,
`ref.null`, `ref.func`, `ref.i31`, `struct.new`, `struct.new_default`,
`array.new`, `array.new_default`, `array.new_fixed`,
`any.convert_extern`, `extern.convert_any`, `global.get` of an
immutable global, and `i32.add/sub/mul`, `i64.add/sub/mul`. The
expression is type-checked like an instruction sequence (operands
matched under subtyping) and must leave exactly one value that matches
the required type. A global initializer may read imported globals and
globals defined earlier; a table initializer may read imported globals
only (the spec validates tables under the context that holds the
imported globals alone). A table without an initializer defaults to
`ref.null`, which requires a nullable element type.

### Segments, start, exports (§3.5.8–§3.5.13)

- Active data segments: the memory exists; the offset has the memory's
  address type (`i32` or `i64`).
- Element segments: the element type is valid; each function index or
  item expression is valid with the segment's type; an active segment's
  table exists, the segment type matches the table's element type, and
  the offset has the table's address type.
- The start function exists and has type `[] -> []`.
- Every export refers to an existing function/table/memory/global/tag;
  export names are pairwise distinct.

## Printing (§6)

The text format allows many layouts (abbreviations §6.1.2, folded
instructions §6.5.11); this package fixes one so that snapshots are
byte-comparable. It is the flat (unfolded) form emitted by
`wasm-tools print` for modules without a name section, minus its
`;; label = @N` / `(;@N;)` comments. Rules:

### Module skeleton

- `(module)` + newline when the module has no printable definition
  (custom sections and empty sections do not count).
- Otherwise `(module` + newline, one definition per line with a
  two-space indent, and `)` + newline.
- Order: types, imports, tables, memories, tags, globals, exports,
  start, element segments, functions, data segments (the canonical
  section order, with each function's signature and body printed
  together at the code section's position).
- Every definition carries its index as a `(;N;)` comment directly after
  the keyword (`(type (;0;) ...)`, `(func (;3;) ...)`, `(import "m" "n"
  (global (;1;) i32))`). Imports come first in each index space; element
  and data segments have their own spaces starting at 0. Indices print
  in unsigned decimal.

### Types (§6.4; abbreviations §6.4.4, §6.4.7, §6.4.15)

- A group encoded with `0x4E` prints as `(rec` on its own line, its
  types on following lines indented by four spaces, then `  )`; an empty
  group prints `(rec)`. The shorthand encoding prints `(type (;N;) ...)`
  directly.
- Sub types: `(sub final? super* comptype)`; a final sub type without
  supertypes prints only the composite type.
- `(func (param t*) (result t*))` — each group omitted when empty, one
  space between types; `(struct (field ft) ...)`, `(struct)` when
  empty; `(array ft)`. A field type is `st` or `(mut st)`; storage types
  are `i8`, `i16` or a value type.
- Value types: `i32 i64 f32 f64 v128`; nullable abstract reference
  types by shorthand — `funcref externref anyref eqref i31ref structref
  arrayref nullref nullfuncref nullexternref exnref nullexnref`; other
  reference types `(ref null ht)` / `(ref ht)` with abstract heap types
  spelled `func extern any eq i31 struct array none nofunc noextern exn
  noexn` and concrete ones as an index.
- A typeuse is `(type T)` followed by ` (param ...)` and ` (result ...)`
  (empty groups omitted) whenever `T` names a function type; it is used
  for function definitions, function and tag imports, tags, and block
  types given by index.

### Imports and definitions

- `(import "module" "name" desc)`, desc one of `(func (;N;) (type T))`
  — imported functions print the bare type reference, without the
  parameter/result expansion used for defined functions and tags —
  `(table (;N;) tabletype)`, `(memory (;N;) limits)`, `(global (;N;)
  globaltype)`, `(tag (;N;) typeuse)`.
- Limits: `min` or `min max`, prefixed by `i64 ` for the 64-bit address
  type (`(memory (;0;) i64 1 2)`). Table type: limits then element type
  (`3 funcref`, `i64 1 5 (ref null 0)`). Global type: `t` or `(mut t)`.
- `(table (;N;) tabletype)` or, when the encoding has an initializer,
  `(table (;N;) tabletype expr)`; `(memory (;N;) limits)`; `(tag (;N;)
  typeuse)`; `(global (;N;) globaltype expr)`.
- Constant expressions print inline: instructions separated by one space
  (`i32.const 1 i32.const 2 i32.add`).
- `(export "name" (func N))`, `(export "name" (table N))`, `memory`,
  `global`, `tag`; `(start N)`.
- Element segments: `(elem (;N;) ` + mode + items + `)` where mode is
  empty (passive), `declare ` (declarative) or `(table T)? (offset) `
  (active; `(table T)` only when the encoding carries an explicit table
  index — including `(table 0)` — and the offset is the constant
  expression in parentheses). Items are `func i*` for the element-kind
  encodings (flags 0–3) and `reftype (expr)*` for the expression
  encodings (flags 4–7), e.g. `(elem (;1;) (i32.const 0) func 0 1)`,
  `(elem (;2;) declare func)`, `(elem (;3;) funcref (ref.func 1)
  (ref.null func))`.
- Data segments: `(data (;N;) "bytes")` for passive segments,
  `(data (;N;) (offset) "bytes")` for memory 0, `(data (;N;) (memory M)
  (offset) "bytes")` for a nonzero memory index.

### Functions and instructions (§6.5, §6.6.7)

- `(func (;N;) typeuse)` on a single line when the body has neither
  locals nor instructions; otherwise the header line, then (only when
  there are locals) one `(local t*)` line listing every local in order
  at four spaces, then the instructions, then `  )`.
- Instructions print one per line, indented four spaces plus two per
  enclosing `block`/`loop`/`if`/`try_table`; `else` and `end` print at
  the depth of the block they delimit. An `if` prints `else` only when
  the encoding contains `0x05`.
- Plain syntax: mnemonic, then immediates separated by single spaces.
  Mnemonics are the text-format names of the specification (e.g.
  `i32.trunc_sat_f32_s`, `v128.load8x8_s`, `i16x8.q15mulr_sat_s`,
  `f32x4.relaxed_madd`, `array.new_fixed`, `ref.as_non_null`).
- Block types: nothing for the empty type, ` (result t)` for a single
  value type, ` (type T) (param ...)? (result ...)?` for a type index.
  `try_table` prints its block type then each clause as `(catch tag
  label)`, `(catch_ref tag label)`, `(catch_all label)`,
  `(catch_all_ref label)`.
- `br_table` prints its labels then the default; `call_indirect` /
  `return_call_indirect` print the table index only when it is nonzero,
  then `(type T)`; `call_ref` / `return_call_ref` print the type index;
  `select` with types prints `select (result t*)`.
- Loads and stores (including vector loads/stores): ` M` when the
  memory index is nonzero, ` offset=o` when the offset is nonzero,
  ` align=2^a` when the alignment differs from the natural alignment
  (the access width in bytes; 16 for full `v128` loads/stores, the
  loaded width for `load8x8`, `load32_zero`, splat and lane forms), and
  for lane forms the lane index last.
- `memory.size`, `memory.grow`, `memory.fill` print the memory index only
  when nonzero; `memory.copy` and `table.copy` print both indices when
  either is nonzero and nothing otherwise; `memory.init` prints the
  memory index only when nonzero followed by the data index;
  `table.init` prints the table index only when nonzero followed by the
  element index.
- Constants: `i32.const`/`i64.const` in signed decimal; `v128.const
  i32x4` followed by the four 32-bit lanes (little-endian) as `0x` plus
  eight lower-case hex digits; `i8x16.shuffle` followed by its sixteen
  lanes in decimal; floats as below.
- `ref.null ht`; `ref.test`/`ref.cast` followed by a reference type
  (`ref.cast anyref`, `ref.test (ref 1)`); `br_on_cast`/`br_on_cast_fail`
  followed by the label and both reference types.

### Floats (§6.3.2)

`f32.const`/`f64.const` print the value in hexadecimal significand
form followed by a comment with its decimal value:

- sign: a leading `-` when the sign bit is set (also for zero, infinity
  and NaN);
- zero: `0x0p+0`; infinity: `inf`; canonical NaN (payload with only the
  top significand bit set): `nan`; other NaNs: `nan:0x<payload>` with the
  payload in lower-case hex without leading zeros;
- otherwise `0x1` + (`.` + the significand's hex digits with trailing
  zeros removed, omitted entirely when the fraction is zero) + `p` +
  the exponent with an explicit sign (`0x1p+0`, `0x1.8p+1`,
  `0x1.99999ap-4`). Subnormals are normalised so the leading digit is 1
  (`0x1.p-149` for the smallest f32: the fraction is empty but the dot
  remains); the f32 fraction uses 6 hex digits before trimming, f64 13;
- the comment ` (;=D;)` where D is `NaN` for any NaN, `inf`/`-inf`,
  `-0`/`0` for zeros, and otherwise the shortest decimal digit string
  that rounds back to the same float (choosing the closest such string,
  ties to an even last digit), written positionally with no exponent —
  `1`, `-1.5`, `0.1`, `10000000000`, `0.0000001`,
  `340282350000000000000000000000000000000`.

### Strings (§6.3.3–§6.3.4)

- Names (import module/field names, export names): a `"`-delimited
  literal with printable ASCII other than `"` and `\` verbatim and every
  other character as `\u{hex}` (lower case, no leading zeros): `"a\u{22}b"`,
  `"\u{e9}"`, `"\u{1f600}"`, `"\u{0}"`.
- Data strings: bytes 0x20–0x7E other than `"` and `\` verbatim, every
  other byte as `\hh` (two lower-case hex digits): `"a\00\ff\22\5c"`.

## Error handling

Malformed input (not generated by the binary grammar, §5.1) must raise
from `decode_module`; invalid modules (violating the typing rules of
§3, see §3.1) must raise from `validate_module`. The tests never inspect the error value
or message, so any raise-based error design works — but the two phases
must be kept apart: a malformed binary must not decode, and a decoded
module that is invalid must print (printing never raises) and then fail
validation.
